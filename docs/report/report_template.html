Abstract

Operational databases are a poor place to run analytics, while classic nightly ETL copies whole tables and delivers stale data. We built a lakehouse that continuously replicates row-level changes from PostgreSQL into Apache Iceberg tables and serves them to SQL analytics with Trino. Debezium reads the PostgreSQL write-ahead log and publishes change events to Kafka; a Spark Structured Streaming job applies each micro-batch to Iceberg with an idempotent MERGE, evolving table schemas automatically. Tables live in S3-compatible object storage (MinIO) behind an Iceberg REST catalog. Airflow orchestrates Spark maintenance jobs — partition evolution, sorted compaction, delete-file rewriting, snapshot expiry and a GDPR-style purge — and Prometheus/Grafana monitor freshness and file health. On TPC-H scale factor 1 ({{load_rows}} rows) the pipeline delivered the full load to Iceberg at {{load_rps}} rows/s end-to-end with checksum-verified correctness, and made individual changes queryable with a median end-to-end freshness of {{fr_p50}} s. Re-laying out the streamed tables removed all {{delete_files_before}} merge-on-read delete files, cut the number of objects in storage by {{objects_saved_pct}} % and made the Trino query suite {{total_speedup}}× faster overall (up to {{best_speedup}}× for a single query).

Keywords: lakehouse, change data capture, Apache Iceberg, Spark Structured Streaming, Debezium, Trino, compaction.

01Introduction and motivation

Businesses want analytics over the same data their applications are changing right now: orders, balances, inventory. Running heavy analytical SQL directly on the operational database competes with transactions, and the traditional alternative — exporting full tables to a warehouse every night — is both expensive (every run copies everything) and stale (data is up to a day old). A lakehouse combines the low-cost, open-format storage of a data lake with the transactional table semantics of a warehouse; change data capture (CDC) feeds it incrementally by reading only the changes from the database log.

The project goal was to implement such a pipeline end-to-end with open-source components and to quantify its behaviour. We call the resulting system Floe — like an ice floe, a slab of Iceberg that keeps drifting with the flow of changes. The concrete objectives were:

  1. Stream inserts, updates and deletes from PostgreSQL into Apache Iceberg tables with Debezium, Kafka and Spark.
  2. Keep the lakehouse correct (identical to the source) and fresh (seconds behind), including when the source schema changes.
  3. Demonstrate Iceberg's schema evolution, time travel and row-level deletes (including GDPR-style erasure).
  4. Counter the small-file problem that streaming creates with compaction and partition optimisation jobs orchestrated by Airflow, and measure query performance and storage before and after.
  5. Make the system observable (Prometheus/Grafana), reproducible (Docker Compose, scripts) and tested (unit, integration, CI).

02Background

Change data capture. PostgreSQL records every committed change in its write-ahead log (WAL). With wal_level=logical a logical replication slot decodes the WAL into row changes; Debezium consumes the slot through the built-in pgoutput plugin, first snapshots existing rows and then emits one event per inserted, updated or deleted row, carrying the new row image, the operation, the commit time and the log sequence number (LSN). Because the slot retains WAL until the consumer confirms it, no change is lost while consumers are down.

Apache Iceberg is an open table format: a table is a tree of immutable files — Parquet data files, delete files, manifests and a metadata JSON file — and a catalog stores an atomic pointer to the current metadata file. Every commit produces a new snapshot, which gives ACID transactions with optimistic concurrency, time travel, schema evolution by column ID, and hidden partitioning whose specification can be changed without rewriting old data. Format v2 adds row-level deletes: with merge-on-read, an update writes the new row plus a small position-delete file instead of rewriting the data file (copy-on-write).

Engines. Spark Structured Streaming processes Kafka in micro-batches with checkpointed offsets; Trino is a distributed SQL engine that reads Iceberg tables directly from object storage.

04Implementation

4.1 Change capture

An initialisation script creates three database roles (application, Debezium with REPLICATION, catalog) and the TPC-H shaped schema shop (region, nation, customer, orders) plus a heartbeat table. The connector configuration is applied idempotently by a one-shot container (PUT /connectors/postgres-cdc/config) that waits until the task is RUNNING. Key settings: plugin.name=pgoutput, decimal.handling.mode=string together with column.propagate.source.type (so numeric(12,2) arrives exactly and with its precision), heartbeats every 10 s, and max_slot_wal_keep_size=4GB on PostgreSQL so a stopped consumer cannot fill the source disk.

4.2 Streaming ingestion into Iceberg

The Spark job subscribes to pg\.shop\..* (new tables are discovered automatically) and handles each micro-batch per table in five steps:

  1. Schema discovery. Each event embeds its schema. The job collects the distinct schemas present in the batch (cutting the message text at the "payload" key, which is much cheaper than parsing every 3 KB event) and merges them, newest first. Debezium logical types are mapped to Spark/Iceberg types (dates, microsecond timestamps, zoned timestamps, decimals from source precision, binary).
  2. Table creation / schema evolution. Unknown tables are created (format v2, merge-on-read, zstd; primary key recorded as a property). New source columns become ALTER TABLE … ADD COLUMN; type changes Iceberg can promote in place (int→bigint, float→double, wider decimal) become ALTER COLUMN … TYPE; anything else is cast to the existing type and logged.
  3. Deduplication. Only the latest event per primary key (highest Kafka offset) is kept.
  4. MERGE. One statement applies the batch:
MERGE INTO lakehouse.shop.orders t USING batch s ON t.o_orderkey = s.o_orderkey
WHEN MATCHED AND s._cdc_op = 'd' THEN DELETE
WHEN MATCHED THEN UPDATE SET …            -- all source columns + CDC metadata
WHEN NOT MATCHED AND s._cdc_op <> 'd' THEN INSERT …

Because the MERGE is idempotent, replaying a micro-batch after a crash (Spark re-runs the last uncommitted batch) yields the same table state; with checkpointed offsets this gives effectively-once results. Commits that collide with a concurrent maintenance job are retried with exponential backoff. Each row carries _cdc_op, _cdc_source_ts (commit time in PostgreSQL), _cdc_lsn and _ingested_at, which enable freshness measurement and change audits. Finally, per-table batch statistics are appended to lakehouse.ops.ingest_batches.

4.3 Maintenance and optimisation

A single Spark job (maintenance.py) exposes the Iceberg procedures as composable steps, and three Airflow DAGs schedule them: hourly housekeeping, a manual layout optimisation, and a GDPR purge. The layout optimisation evolves orders to PARTITIONED BY months(o_orderdate) with sort order (o_orderdate, o_custkey) and sorts customer by (c_nationkey, c_custkey), then runs rewrite_data_files (sort strategy, 128 MB target, all deletes applied, partial progress so commits stay small), rewrite_position_delete_files, rewrite_manifests, expire_snapshots and remove_orphan_files. Partition evolution changes only metadata: the streaming job keeps running and immediately writes new data in the new layout. Orphan removal is fed with an S3 listing through file_list_view and is restricted by Iceberg to files older than 24 h, so files of in-flight commits are never deleted.

4.4 Monitoring, testing and reproducibility

A custom Prometheus exporter writes a heartbeat row into PostgreSQL every 15 s and reports how old the newest heartbeat visible through Trino is — the true end-to-end freshness — together with replication-slot lag, connector state, ingest rate, MERGE duration and per-table data/delete files, bytes and snapshots. Prometheus also scrapes Spark's built-in streaming metrics and MinIO. Alert rules fire on stale data, a stopped connector, WAL growth, small-file accumulation and a stalled stream. Correctness is checked by comparing row counts and an order-independent checksum() over all columns between the postgresql and lakehouse catalogs in Trino. The repository contains unit tests (type mapping, evolution rules, configuration), a full-stack integration test (load → workload → update/delete → schema change → maintenance, each followed by a consistency check), a GitHub Actions workflow, and scripts for setup, the scripted demo and clean-up.

5.5 Fault tolerance (observed)

During the first freshness measurement the Docker VM ran out of memory and the operating system killed the Spark driver. The container restarted automatically, resumed from the checkpointed Kafka offsets and re-applied the interrupted micro-batch; because the MERGE is idempotent, no change was lost or duplicated and the subsequent consistency checks passed. The incident is visible in that measurement: median freshness stayed at {{inc_p50}} s, but the probes caught in the restart took up to {{inc_max}} s ({{inc_n}} visible, {{inc_timeout}} timed out). Memory limits were then reduced so that the steady-state total leaves headroom in the 8 GB VM, and freshness was re-measured (Section 5.2).

Row counts and full-row checksums of every table were identical between PostgreSQL and Iceberg before and after the optimisation (Table 5); this check also ran after the initial load, after the workload, after a full replay of the Kafka topics into an empty lake, and in the integration test.

5.7 Functional demonstrations

  • Schema evolution: ALTER TABLE … ADD COLUMN and an integer→bigint change in PostgreSQL reached Iceberg within about 10 s as metadata-only changes; old rows read NULL for the new column.
  • Time travel: the same order queried as of the current snapshot, a snapshot id and a timestamp returned the new and the old values; the CDC columns allow auditing which rows changed since a snapshot.
  • GDPR erasure: a customer deleted in PostgreSQL disappeared from current queries within about 10 s (as position deletes) but was still readable through time travel; the purge DAG rewrote the affected files and expired history, after which the old snapshot no longer existed.

The main lesson is that the hard parts of CDC ingestion are operational: concurrency between writers, metadata growth, small files and observability matter as much as the happy-path data flow, and each is easier to get right with an explicit correctness check that can be re-run at any time.

07Conclusion and future work

The project delivers a working, reproducible CDC lakehouse: changes made in PostgreSQL become queryable in Iceberg within seconds, the copy is provably identical to the source, schemas evolve without intervention, history is queryable and can be erased on request, and scheduled optimisation turns the streaming-induced small files into a layout that makes analytical queries {{total_speedup}}× faster while cutting the number of stored objects by {{objects_saved_pct}} %. Limitations are the single-node deployment, a 10 s minimum freshness from the micro-batch trigger, and that dropped source columns remain in Iceberg. Natural extensions are a comparison with Apache Hudi on the same workload, column-level lineage with Apache Atlas or OpenLineage, Avro with a schema registry to cut serialisation cost, deployment on Kubernetes (AKS) with Azure Data Lake Storage and Event Hubs, and Flink for lower-latency ingestion.
